# Particle fidelity review

The expanded [implementation handoff](particle-fidelity-handoff.md) contains the source map, proposed architecture, staged implementation tasks, and validation procedures. The [preserved benchmark runner](benchmarks/particle-fidelity.mjs) and [original result summaries](benchmarks/particle-fidelity-baseline.json) make the CPU investigation reproducible without relying on temporary files.

Reviewed the local working trees on 2026-09-23: `screean-components`, `../screean`, and `../../personal/flowfield`. Existing uncommitted changes were included in the review and left untouched. This is a source review with a CPU physics benchmark; visual parity and browser/GPU frame times remain unmeasured.

Comparable particle density and coherent motion look achievable while keeping the DOM-first component architecture. The current gap comes from conservative particle counts, different motion, and a component controller that still uses CPU simulation. There is no fixed bitmap-resolution ceiling that explains the difference. Matching the exact projected 3D appearance of `flow` would require additional depth support.

The early performance constraint was explicit. The engine's [scale RFC](../../screean/docs/RFC-scale.md) says physics stays on CPU until profiling justifies GPU physics. That is historical rationale, not proof of a current hardware limit. GPU physics now exists, but [the component controller](../../screean/src/screen/controller.ts) constructs `new World()` and uses the synchronous WebGL2/Canvas2D renderer factory.

| Aspect | Personal `flow` GPU path | Component transitions |
| --- | --- | --- |
| Particle population | A requested 25,000 becomes 65,536 because the compute texture rounds each dimension to a power of two | Usually 1,200–6,000 per component; button default is 3,000 |
| Simulation | Position and velocity remain in GPU textures | Mutable JavaScript particle objects, CPU forces and reform loop |
| Motion | Three-octave 3D curl noise, animated through 4D simplex noise; optional domain warping and orbital forces | Radial impulse, drag, neighbor repulsion, pointer force, color-based sinusoidal shimmer |
| Presentation | Perspective points; opacity decreases with particle count; theme selects normal or additive blending | Gaussian sprites; fixed size; additive blending by default; palette colors |
| Lifetime | Persistent simulation | Default free phase is 700 ms, followed by spring reform and DOM reveal |

Saved user settings may select a different flow population. These are code defaults and allocation behavior, not a reading of the user's running session.

1. **Count settings currently hide an important override.** Every headless component supplies its own count, even when its caller omits `particleCount`. Raising the provider/controller count therefore does not raise the default button or toggle count. The precedence should be explicit in any fidelity controls. The constants describe their purpose as keeping concurrent transitions affordable, but counts are fixed by component type rather than measured area. A larger card does not automatically receive more particles. Some story tiles use still lower explicit counts. See [button construction](../src/components/headless/button.ts) and [story examples](../site/stories/components.ts).

2. **The noise responsible for flow's appearance is absent from component transitions.** Shimmer derives its phase from color, so particles with identical colors receive identical shimmer acceleration. It is not a spatial flow field. Both local flowfield experiments use stacked sine/cosine functions; even the separate 80,000-particle GPU experiment does not reproduce the personal repo's curl-noise algorithm. Increasing either count or shimmer strength cannot supply the missing structure. See [engine forces](../../screean/src/core/forces.ts), [local CPU flow](../site/lib/physics/flowfield.ts), and [local GPU flow](../site/experiments/flowfieldGpu.ts).

3. **Neighbor repulsion becomes expensive precisely when a component is dense.** The CPU spatial hash reduces the search area, but many particles packed into a small button still produce many neighbor comparisons. Repulsion also pushes against the dense overlapping appearance being sought. Flow's GPU velocity shader uses a sampled field without particle-to-particle repulsion. Moving the existing force stack unchanged to GPU would retain another problem: the engine's [GPU repulsion kernel](../../screean/src/core/gpu/kernels.ts) explicitly scans all particles for every particle. At 65,536 particles that is about 4.3 billion loop iterations per dispatch. The dense mode should omit this force, or use a separately profiled approximation.

4. **The drawing settings need to become part of the fidelity controls.** The controller fixes `particleSize` at 0.8 and `trailAlpha` at 0.22, and does not expose size, opacity, or blending. The WebGL shader makes that size a 1.6 CSS-pixel-wide quad at zero depth. Flow's default point size is 4 framebuffer pixels before depth scaling, so the two numbers cannot be compared without accounting for DPR. Both paths already use device pixel ratio by default. Raising resolution alone is unlikely to solve the problem. Flow also scales opacity by particle count; the component path has no equivalent compensation. Simply adding more additive sprites can saturate the cloud. See [WebGL renderer](../../screean/src/renderers/webgl/WebGLRenderer.ts) and [controller options](../../screean/src/screen/types.ts).

5. **Component image fidelity is a separate limitation.** The [bitmap sampler](../../screean/src/fields/bitmap.ts) samples uniformly among pixels above an alpha cutoff, with replacement and jitter. It does not allocate particles by pixel color or edge detail. The controller then assigns palette colors instead of sampled image colors. For an opaque button, its label does not receive special treatment because the background is also opaque. More particles can improve coverage, but cannot recover discarded text/image colors. DPR-aware rasterization already exists in [bitmapFromElement](../../screean/src/fields/bitmapFromElement.ts).

CPU measurements used the current engine source bundled with esbuild, Node 25.1.0, and an Apple M4 Pro. Each case used a seeded uniform rectangular population, the controller's `soft` forces, spring weight zero, no active pointer, and its default radial kick of 420. After code warmup, three fresh populations each ran 43 steps at 1/60 second. The table reports the median first step and the 95th percentile of subsequent steps across trials. Geometry is synthetic, not a rasterized production component.

| Starting area | Count | Default first step | Default subsequent p95 | Repulsion disabled first step | Repulsion disabled subsequent p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 160 × 48 CSS px | 6,000 | 10.99 ms | 10.09 ms | 0.87 ms | 1.33 ms |
| 160 × 48 CSS px | 25,000 | 163.78 ms | 112.93 ms | 3.51 ms | 4.00 ms |
| 160 × 48 CSS px | 65,536 | 1,258.08 ms | 614.07 ms | 9.52 ms | 10.21 ms |
| 640 × 360 CSS px | 6,000 | 3.77 ms | 4.24 ms | 1.03 ms | 1.63 ms |
| 640 × 360 CSS px | 25,000 | 21.32 ms | 22.18 ms | 4.10 ms | 4.59 ms |
| 640 × 360 CSS px | 65,536 | 93.75 ms | 94.46 ms | 10.89 ms | 11.02 ms |

These exclude rasterization, target sampling, React/DOM work, reform, instance packing, upload, and rendering. They are not browser FPS measurements. Disabling repulsion also changes subsequent trajectories; the first-step comparison starts from identical positions and velocities and best isolates its immediate cost.

As a second diagnostic, disabling repulsion and adding the engine's existing three-octave CPU Perlin force produced subsequent p95 costs of 8.75 ms at 25,000 particles and 22.74 ms at 65,536 in the button case. This is not flow's more expensive curl noise. It supports moving dense field evaluation to the GPU or sampling a shared field grid rather than directly evaluating complex noise per CPU particle. Run `node docs/benchmarks/particle-fidelity.mjs` from the component repository to reproduce the full experiment against current engine source.

The existing GPU engine is useful groundwork, but it is not a controller option that can simply be enabled. The controller owns `Particle[]` slices, direct per-particle reform updates, impulses, and retirement. A GPU implementation needs equivalent operations over stable slice ranges, including concurrent transitions. Its renderer must consume the same GPU buffer on the same device without per-frame readback. The engine already provides [drawFromBuffer routing](../../screean/src/core/render-world.ts), which should be reused.

The existing GPU Perlin kernel also needs review before reuse for coherent motion. [WorldGPU](../../screean/src/core/gpu/WorldGPU.ts) sets its shared seed to `seed ^ frameCounter`, and the Perlin shader uses that value to construct the spatial field. This changes the field every frame instead of smoothly evolving a stable field. It is two independent scalar noise components rather than curl noise, and its velocity addition omits `dt`, unlike the CPU force integration. Those differences are visible in source; their visual impact has not been measured here. The CPU `perlinForce` is also absent from the package's public barrel.

Recommended implementation sequence:

1. Add an opt-in fidelity experiment using the existing transition controller. Compare counts of 6k, 16k, 32k, and 65k, with separately adjustable dot size, opacity, blending, noise, and repulsion. Include button, text, large card, and overlapping transitions. Keep timing and camera/viewport conditions fixed when comparing samples. Begin with no trails so dot density can be judged directly.
2. Add coherent curl motion and configurable presentation to the shared engine controller. For an initial CPU experiment, evaluate a shared 2D field grid and interpolate per particle. Preserve each particle's component target separately from flow motion. Fade the flow contribution out during reform. A 2D field can test density and motion, but should not be presented as exact parity with flow's projected 3D volume.
3. Implement the dense GPU path in the shared controller architecture, reusing WorldGPU and its direct-buffer renderer. Upload component targets at capture time, keep motion and reform on GPU, and omit pairwise repulsion for this mode. Preserve DOM ownership, concurrent slice isolation, transition cancellation/disposal, and the CPU fallback. Retain compatibility for consumers of the controller's CPU `world()` accessor rather than silently changing its behavior.
4. Replace fixed-only counts with an opt-in area/density policy and a shared budget for concurrent transitions. Normalize opacity against projected density and dot footprint. If faithful text/images during reform are required, extend sampling to preserve colors and reserve samples for fine details; uniform alpha-mask sampling alone cannot provide that.

Before selecting production defaults, measure full browser frames at DPR 1 and 2, capture latency, initial burst, free motion, reform, and multiple simultaneous components. Compare normal and additive blending on light and dark backgrounds. Test the GPU path on target devices and the CPU fallback separately. A 60 Hz frame has about 16.7 ms for all work; the CPU results here justify a GPU prototype but do not establish a safe production particle budget.

No runtime behavior changed in this review. The recommended next change is the controlled fidelity experiment plus shared controller controls, followed by GPU integration once the desired appearance is established.
